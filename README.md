# Luminary

Luminary - Python-проект (FastAPI + SQLAlchemy) с архитектурой, ориентированной на модульность и DDD-подход. Исходники находятся в папке `src`, пакет проекта - `luminary`.

## Структура проекта

- `src/` — исходный код проекта
  - `common/` — общие библиотеки (инфраструктура, интерфейсы, реализации сервисов)
  - `luminary/` — основной пакет приложения (assistant, chat, model, source и т.д.)
- `tests/` — юнит и интеграционные тесты

## Требования

**Запуск в Docker:** Docker Engine и Docker Compose.

**Локальная разработка:** Python 3.11+, Poetry.

## Запуск с Docker Compose

1. Клонируйте репозиторий и перейдите в корень проекта (где лежит `docker-compose.yaml`).

2. Создайте внешнюю сеть Docker (в `docker-compose.yaml` она помечена как `external`):

```powershell
docker network create luminary
```

3. Скопируйте пример переменных окружения и при необходимости отредактируйте (ключи API, пароли, порты на хосте):

```powershell
copy .env.example .env
```

4. Поднимите сервисы (образы приложения и миграций соберутся при первом запуске):

```powershell
docker compose up --build
```

Для фонового режима добавьте `-d`:

```powershell
docker compose up --build -d
```

**Что поднимается:** PostgreSQL, RabbitMQ, MinIO (S3), Qdrant, контейнер миграций Alembic, приложение FastAPI (uvicorn на порту **8000** внутри стека) и **nginx** на порту **80** на хосте.
Управление RabbitMQ и консоль MinIO доступны на портах из `.env` (`RABBIT_MANAGEMENT_PORT`, `MINIO_CONSOLE_PORT`).

Остановка:

```powershell
docker compose down
```

Для удаления томов добавьте `-v`:

```powershell
docker compose down -v
```

## Управление папками и порядком чатов

Папки сохраняют состояние `collapsed`. Порядок папок и чатов представлен
строковым `order_key` (fractional indexing): при перестановке сохраняется только
перемещаемый объект, а не весь список. В ответах API поле `order_key` заменяет
прежний `sort_order`; клиенты должны использовать новый формат запросов.

`PUT /api/v1/folders/order` принимает:

```json
{
  "folder_id": "UUID перемещаемой папки",
  "previous_folder_id": "UUID предыдущей папки",
  "next_folder_id": "UUID следующей папки"
}
```

`PUT /api/v1/chats/order` принимает аналогичные поля `chat_id`,
`previous_chat_id` и `next_chat_id`. Чат и его соседи должны принадлежать одному
пользователю и находиться в одной папке либо в корне. Для первого элемента
предыдущий сосед — `null`, для последнего следующий — `null`; оба — `null`, если
других элементов нет. Соседей выбирают после исключения перемещаемого объекта
из текущего списка. Ключи генерирует сервер; порядок регистрозависимый.
Новые ключи включают фиксированный суффикс с UUID перемещаемого объекта:
параллельные перестановки разных объектов между одинаковыми соседями не
создают одинаковых позиций. Сохраняется только перемещаемый объект.
Уже сохранённые ключи не переписываются; если в старых данных есть одинаковые
позиции, один из этих объектов нужно переставить относительно соседей с
разными ключами (или на край списка).

Перенос: `PUT /api/v1/chats/{chat_id}/folder` с `{"folder_id": "UUID папки"}`
или `{"folder_id": null}` для корня. Собственные источники чата сохраняются;
источники старой папки не копируются. В новой папке используется её контекст.
При переносе прежняя ручная позиция сбрасывается в позицию по дате создания.
Связь чата с папкой синхронизируется обработчиком `ChatMovedEvent`.

Удаление папки мягкое. Обработчик `FolderDeletedEvent` мягко удаляет её чаты,
но не источники. По согласованному решению ревью строки связей `folder_chats`
и `folder_sources` сохраняются. Обработка событий асинхронная и требует
работающего потребителя RabbitMQ; после ответа на удаление/перенос проекция
папки может обновиться не сразу.
Отдельные `ChatDeletedEvent` при удалении папки намеренно не публикуются:
контракт каскадного удаления — `FolderDeletedEvent`, а связи удалённой папки
сохраняются. Новые потребители событий удаления должны учитывать оба сценария.

Обработчики переноса/удаления удерживают блокировку до завершения общей
транзакции, читая актуальное состояние через интерфейс репозитория модуля,
которому принадлежит объект. Репозитории записи не обращаются напрямую к
чужим ORM-моделям. Сохранение папки обновляет только изменённые поля и
конкретные добавления/удаления связей, не перезаписывая их старый снимок.

Миграция `6d42f8c91b03` добавляет nullable `order_key` без массового обновления
существующих строк. Для строк без ключа порядок вычисляется из `created_at DESC`
и UUID, поэтому сохраняется прежний порядок. В этой ещё не слитой ветке сама
миграция была изменена по ревью. Если её старый вариант уже применён, одного
`alembic upgrade head` недостаточно: для тестовой БД нужно пересоздать схему
либо сначала откатить миграцию **старой версией её файла**, затем применить новую.
БД с нужными данными нельзя очищать; для неё потребуется отдельная миграция.

Проверки (интеграционные тесты создают временные контейнеры, нужен Docker):

```sh
poetry check --lock
poetry run ruff check src tests cli
poetry run mypy src tests cli
poetry run pytest -q
poetry run black --check src tests cli migrations/versions/6d42f8c91b03_folder_management.py
```
